# Dyce broker email approval page and DNA Hub

## index.html: the approval page

A single static page. An approver opens it from the link in an approval email; it shows the broker email in full and records Approve or Reject through the comms-approve function in Dyce's database project.

It holds no data and no keys. The one-use link token arrives in the address fragment and is sent only to that function.

Source of the logic: Dyce-Energy-Ltd/dyce-spine, supabase/functions/comms-approve. Owner: Phil Brook.

## hub.html: the DNA Hub

`hub.html` is one sign-in for Dyce's tools. People on the hub's list sign in with an emailed 8-digit code; anyone else is turned away. It holds no data and no keys; it talks only to the comms-web function in Dyce's database project, the DNA Viewer tab to the dna-viewer function there, and the Pricing tab to the dna-pricing function there. The session token is kept in this browser's localStorage (key `dyce.hub.token`), and the last tool and menu item used under `dyce.hub.where`.

A navy rail down the left shows each tool the person may use, with the open tool's menu beneath its name, and the signed-in address and Sign out at the foot. Clicking another tool's name opens it with its menu showing; clicking the open tool's name folds its menu away or brings it back, leaving the page as it is (`tools/rail-preview-check.js`, run by `tests/test_build.py`, checks this in a headless browser); a line above the content says where you are. A soft glow of the Stage magenta tint sits behind the current menu item and follows the pointer or keyboard focus over the rail, and a row under the pointer in the content fills with the magenta tint with a magenta rule on its left edge (Phil Brook's choice, 13/11/2026; the gradient agreed with Chris Beardsmore). At phone width the rail sits above the content. What a person sees follows their ticks, set in DNA Admin; the database checks the tick again on every call, so hiding a tab or menu item is tidiness, not the gate.

**Pricing.** The tab calls the `dna-pricing` function (`/functions/v1/dna-pricing`, a POST with `op` and the hub session `token`); the function checks the session and the op's tick every time, so hiding a screen or a button is tidiness. It has four screens. The wording was shortened and the screens reworked on 18/11/2026 (Adam Young's review, Phil Brook to review): the preview became a table of annual cost by usage and term, Band sets and splits became Margins and Splits, Margins gained Manage and a save bar, and the Live price book gained Check a price. *Supplier files* lists every file newest first with the state the database gives it: Loading, Ready to price (the database's awaiting_bandings), Applying, Live, Replaced, Load failed, or Loaded before the pricing tool. Files arrive from the Partner Sales SharePoint folders through the pricing loader in dyce-data-pipelines; a file the loader could not read is listed under *Files that failed to load* with the reason. Files are not loaded by hand: the Load a file card was removed (Phil Brook, 19/11/2026), so files come in only through the SharePoint loader. Above the list, *Price books* (Phil Brook, 20/11/2026; `pricing/health.js`) has one row per Base Prices folder the loader reads (Voltx electricity, Yu electricity, Yu gas, Jellyfish electricity, Jellyfish gas): the newest file, when it arrived with its age in UK calendar days, rows loaded and its state; a file that failed to load after the newest good one shows as *Newer file failed* with its reason. Each price book's name opens its SharePoint folder in a new tab, where a new file is saved; the folder list `BOOKS` must stay in step with `pricing_loader/folders.js` in dyce-data-pipelines. The adapters in `pricing/adapters.js` are kept in step with the loader's copy (its drift test) but nothing in the page calls them now. Jellyfish electricity files from 16/11/2026 are priced by NDA band, read from `tnuosResidualBand` (LV_NoMIC_1 to LV_NoMIC_4 are NDA bands 1 to 4; an older file without the column loads with no band). The adapter keeps one row per price key (the columns of `base_rate_price_key`): a price Jellyfish gave by DUoS tariff ID, for MHHS-migrated meters, is left out where an LLFC price has the same key and kept only where none does; LLFCs in one band at one price load once; different prices for one key are all refused. Jellyfish rows with a 3-month term load like any other term (Phil Brook, 20/11/2026, keeping his 24/09/2026 ruling that short terms are sold for co-terming), and a Jellyfish electricity file named `...-llfc.csv` (their LLFC-only book of 16/11/2026) is refused (Chris Beardsmore's change note of w/c 16/11/2026, applied by Phil Brook 20/11/2026). Rows left out are counted, with the reason, under What this format assumes; the row count sent to the database is rows loaded plus rows rejected, which is what publishing checks. The newest finished file of each supplier and fuel, whatever its state, has *Price* (*Reprice* when it is live), which opens the workspace. Since 20/11/2026 (Phil Brook: product changes are few and small, so the screen should open on what is in use and be cleaner, with as few dropdowns as possible) it opens on the *current product configuration* with its products chosen for acquisition and renewal alike, and the grid, chart and preview showing at once. Since 20/11/2026 (Phil Brook) the current configuration is what is live: `book_live` names the product (band set) each live run priced with (`price_config_id`, `config_key`, `config_name`, `config_version`, `named`; dyce-spine's dna-pricing). The live rows for the file's supplier and fuel with `named` true are taken by `config_name` (`liveChoice` in `pricing/grid.js`; the older unnamed runs are left out); if acquisition and renewal have the same products they are one choice for both, otherwise the screen opens with acquisition and renewal already kept apart. If an active product configuration (the supplier's first, then one for every supplier) holds exactly those products, the line under the heading names it: "Current product configuration: Advanced range (live since 11/11/2026)."; if none does, it says "Current: the live products (no saved product configuration matches). Live since 18/11/2026.", and a change is named with the dated new-configuration name as below (a change is needed to save). The same line says plainly when the sale types differ, when a live product is no longer a product (retired, so not loaded), and when a product is live at an older version than the one the grid shows. With nothing named live for the supplier and fuel (or if `book_live` cannot be read), it falls back to the most recently saved active product configuration for the file's supplier, else for every supplier, else none (`currentConfig`; a configuration's date is the newest save among its members, because `band_sets` gives a bundle no date), and the line says "Current product configuration: Alpha November (not live yet)." or "(the most recently saved). Prices live since 11/11/2026: Standard and Gold.". Discard changes goes back to whatever the screen opened on. The main view holds that line, the grid with the chart beside it (above the grid only the Margin and Standing charge share tabs and the selection bar; the Cell detail shows only once a cell is clicked), the Preview (region, the one dropdown kept, starting at the first region, and the usage box), and the action bar. Everything else is under *More options*: *Use a different product configuration* (the supplier's and every supplier's, click to load; loading one starts again from it and drops unsaved changes), the chosen products with Remove and Add a product (only the file's supplier's and every supplier's), *New product* (the same form as on Margins; a fuel with no products also has New product in the grid's empty column, and still shows its ladder's bands, so a file can be banded from nothing), *Separate acquisition and renewal* (a list for each sale type; a new product is then kept for the sale type chosen in its form), and the grid's Columns switch. Splits are on the Splits screen only, not on the Price screen (Phil Brook, 19/11/2026). Any change to a margin, share or cost, or a product added or taken out, shows one line above the buttons: *New product configuration:* with a name box filled in as "<Supplier> <fuel> <DD/MM/YYYY today>" (with " (2)", " (3)" and so on when that name, or a product it would make, is taken; `defaultConfigName`), Discard changes, a line saying what will be saved, and the reason. Splitting the same products between acquisition and renewal is not a change. *Save* (Set tick) and *Apply* then save a new product configuration under that name for the file's supplier: each changed product as a new product "<configuration name> <product type>" with that supplier, a product made with New product under its own name, the unchanged products as they are, and the configuration the screen started from left unchanged; a typed name already used is refused in a plain sentence. Save changes no price and nothing goes live; the screen is read again working from the new configuration. With no change Save is hidden and Apply applies the configuration's products as they are, saving nothing. Versions of a product are made on the Margins screen, not here. Edits are held in the page until Save or Apply. One product per product type in each sale type, up to eight; a blank product stays blank, and the preview waits, saying which product to fill, until every band of every chosen product has a margin and a standing charge share. The preview (`preview_selection`) shows the warnings first (each attention code as a sentence), then a table with a row per usage and term and a column per product, each cell the new annual cost with the change against the live price and the margin, for acquisition or renewal; every figure the function gives is under *All rates and margins*. It refreshes a moment after each change. Regions show by name alone, without their code (Phil Brook, 19/11/2026). If only acquisition or only renewal has products, the page says that the other side will have no prices once applied. *Apply* saves first when there is a change (one `band_sets_save` with the reason, then `bundle_save`), previews again and refuses, keeping the edits, if the list of items needing attention is not the one the person read; it then sends the count and fingerprint of the list that was read, and the box "I have checked the N warnings" in the action bar must be ticked when N is above zero. Each Apply replaces the whole live set for that supplier and fuel. After an Apply the page checks the book every 10 seconds for up to 5 minutes, then makes the Broker and UD Upload files for each new electricity run (`pricing/exports.js`), stores them and records them. *Margins* is one screen for one fuel at a time, laid out as Phil Brook's Margins mockup (look agreed 19/11/2026, without the mockup's Where prices stand table and its Live prices and New prices tabs, whose jobs are on Supplier files and Live price book): Fuel, Columns (by product configuration or by product type) and Showing (margin p/kWh or standing charge share %) as segmented switches; the selection bar (Selected, a Value box, Shift by value, Set to value, Copy a column into selection, Select all) and its hint; the chart card beside the grid, drawn at its own width and 330 pixels high so that the chart and the grid's bands fit on one 1440 by 900 screen (Phil Brook, 19/11/2026), with the grid scrolling sideways inside its box when it is wider than its share (margin by band for the products ticked in the grid's On chart row, four at most and the first four to start, with a crosshair and a readout line, names at the line ends, and points that drag to change a margin); the grid, a hairline spreadsheet with a row per band of the fuel's band ladder, each cell the margin (or share) with the annual margin at the band midpoint under it, changed cells tinted, paste from Excel; and under them the Cell detail in two columns (once a cell is picked: what it earns at the midpoint, the standing charge and unit rate split, the cost per meter and product type, and the versions of its product with Restore as a new change). The foot counts the changed cells and products, with Discard changes and Review changes; the review lists each changed product's changes and asks for one reason, and its Save saves every changed product together as new versions (`band_sets_save`). Margins have no cap; a band with no margin or share, or a margin not above zero, is listed under Check before saving and stops Save. New product, New product configuration, Edit product configuration members, Edit ladder, Retire product and Retire product configuration are under *Manage products* and need the Set tick. On the Pricing tab a bundle is called a *product configuration* in everything a person reads (Phil Brook, 19/11/2026); the code, the dna-pricing ops (bundle_save, bundle_retire) and the database keep the name bundle. Likewise a band set is called a *product*, and what used to be called the product (Standard, Gold, Silver, Advanced Saver) is the *product type* (Phil Brook, 19/11/2026); op names such as band_sets_save and the database keep the old words. With no products for the fuel (as in dyce-prod on 20/11/2026) the screen keeps the whole layout: the switches and the selection bar greyed out, the chart card with its axes over the fuel's bands, the grid's corner cells with a row per band and New product in the empty column (Set tick), and the Cell detail; the Price screen's grid does the same. The Price screen's grid is the same grid, chart and cell detail. *Splits* shows each supplier's splits (electricity only; publishing a split reprices nothing): the live split, a draft to publish, the estimate from the latest file, and the form for a new draft behind *Change split*. A product or product configuration may name a supplier, or none for every supplier (Phil Brook, 19/11/2026): the Price screen's More options lists only those for the file's supplier and those for every supplier, a new product configuration made on the Price screen is for the file's supplier, New product and the product configuration form on Margins have an optional Supplier (None by default), and the Cell detail shows the product's supplier (All suppliers when none). The page sends `supplierId` (a supplier id, or null for every supplier) on each set of `band_sets_save` and on `bundle_save`, and reads it from each band set and bundle of `band_sets`. Every save and every preview item carries the ladder the screen was opened with, and the database refuses it if the ladder has changed since. A product saved against an older ladder is marked *Older ladder* and its margins are carried to the current ladder where a band keeps its lower bound; if every band was carried it counts as changed and the next save saves it on the current ladder, otherwise its blank bands must be filled first, and until then it cannot be applied. *Live price book* shows any failed update with Abandon update, then *Check a price* (supplier and fuel, region, usage: unit rate, standing charge and annual cost for each live product type, sale type and term, from `book_check`, which reads `pricing.preview_run` on each live run: single-rate standard prices), then the live prices, each run with a *Files* menu: the Broker and UD Upload files (`output_link` gives a 60-second signed link) and, with Publish, Rebuild files. **Mailing groups.** Step 3 of New email opens with a menu, *Who is it for?*: *Broker primary email (HubSpot company)* (the default, the brokers list as before) or *Broker Contact Segment*. Choosing the segment calls `segment_refresh`, shows the stored copy from `segment` at once, then asks `segment` every 2 seconds for up to 60 until the run has finished (told apart from the earlier run by its `started_at`, never by the browser clock), and ticks every contact. A line above the list gives the time of the copy in London time, or the failed fetch and the copy still shown; *Fetch again* repeats it. The list has the columns Email, Primary Associated Company ID and Name, and search matches any of them. Ticks are kept apart for each group and cleared when the group changes. Requests and previews carry `recipient_group` and either `broker_keys` or `contact_ids`, never both. The approval page says `N addresses in the Broker Contact Segment` for a segment send. In the preview, `?segmentfail=1` makes the stub's fetch fail.

The Renewals items show what the renewals journey will send at its 09:30 weekday run in the next 10 days, grouped by the day each email goes, with the reason for any that will not go; the renewal emails already sent, 50 at a time, each viewable as stored in a sandboxed frame; and the stopped brokers. They never send anything, and while the journey's redirect is set they say where every email goes. The DNA Viewer tab is the laptop contract library moved into the hub, behind three ticks: View (search, account pages, reporting, opening documents and invoices), Review queue (the queue, a folder's page and its actions) and Originals (opening a file's original, with its bank details). Its pages come from the dna-viewer function and are shown only after the page's allowlist sanitiser.

The Commission Engine tab is the laptop's commission app moved into the hub one piece at a time, behind the `commission.*` ticks; piece 1 is View, read-only. Its pages (Lines, Exceptions, Decisions, Runs and the run, line and decision they link to) come from the commission-engine function as `{title, html}`, and are shown only after the same allowlist sanitiser as the DNA Viewer's. Links and filter forms become page calls to the function with their path and every value of every parameter (`{name: [values]}`, so ticking two choices of a filter sends both); only the function's seven paths are followed. The Broker filter's search hides names in the page as you type, never a ticked one, and asks the function nothing. A link that moves the page under another menu item (a line's run, a decision's line) moves the menu mark, the line above the content and `dyce.hub.where` with it. Nothing from these pages is stored: localStorage keeps only the hub's `dyce.hub.where`, and sign-out empties the tab.

The Dashboard Pool tab is the voting round on the candidate dashboards, behind one tick, Review; the decider (Phil Brook, whose address is written only into the database function) sees the tab without it. *Boards* lists the boards by area in the side menu with each person's own mark (Keep, Maybe, Drop, Pass or To review) and any decision, and shows the chosen board's screen, how each question is answered, the vote (with audiences on Keep and Maybe, and a note) and everyone's votes; *Summary* gives every board's counts and decision. It calls the `pool_*` actions of `comms.web_call`. The boards, figures and votes are held in the page's memory only and dropped on sign-out; localStorage keeps only the open board's id (`hub.pool.board`). `me` says who decides (`is_decider`, true for the decider alone), so the tab shows for the tick or for `me.is_decider`, and nobody without the tick asks `pool_state`.

**Dashboard Pool decisions.** The decider's parts follow `me.is_decider` in `pool_state`, which also carries, for the decider only, `reviewer_count` and `current` on each vote. Each board shows *N of M reviewers have voted* (current reviewers with a vote, Pass included, of all current reviewers; a count only, never who has not voted), the audiences picked with how many picked each, and each vote by someone no longer a reviewer marked *(former reviewer)*. *Your decision* has audience ticks, starting from a kept decision's audiences or else the most-picked audiences, then *Keep this board* (`pool_decide` with the ticks), *Drop this board* (`pool_decide` with none) and *Clear decision* (`pool_clear`); a tick alone saves nothing. *Votes changed since decided* shows beside the decision, in the board list and in the Summary when a vote is newer than the decision (a vote sent again unchanged keeps its time); saving the decision again, changed or not, is always sent and clears it, as the server gives the decision a new `decided_at`. The side menu adds the filters *Awaiting decision* (no decision yet) and *Votes changed since decided*; the Summary adds *N of M voted*, the flag, and a *Reviewer* filter that shows one person's votes. In the preview, `?as=admin` is the decider with the tick, `?as=reviewer` a reviewer, and `__stub.poolVote(email, board, verdict, audiences, note)` in the console records a vote by someone else (for example Sam Example after a decision), shown when the tool is next opened.

## send.html: forwards to the hub

The broker emails page is now part of the DNA Hub. `send.html` only forwards the browser to `hub.html` (a meta refresh and a link); it has no script. The hub removes the old page's localStorage keys (`dyce-send-token`, `dyce.tab`) when it opens.

## The shared origin

All GitHub Pages sites of the Dyce-Energy-Ltd organisation share the origin `https://dyce-energy-ltd.github.io`, so they share the hub's localStorage and the comms-web CORS allowance. **No other repository in the organisation may enable GitHub Pages** unless the hub first moves to its own domain.
