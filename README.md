# Dyce broker email approval page and DNA Hub

## index.html: the approval page

A single static page. An approver opens it from the link in an approval email; it shows the broker email in full and records Approve or Reject through the comms-approve function in Dyce's database project.

It holds no data and no keys. The one-use link token arrives in the address fragment and is sent only to that function.

Source of the logic: Dyce-Energy-Ltd/dyce-spine, supabase/functions/comms-approve. Owner: Phil Brook.

## hub.html: the DNA Hub

`hub.html` is one sign-in for Dyce's tools. People on the hub's list sign in with an emailed 8-digit code; anyone else is turned away. It holds no data and no keys; it talks only to the comms-web function in Dyce's database project, the DNA Viewer tab to the dna-viewer function there, and the Pricing tab to the dna-pricing function there. The session token is kept in this browser's localStorage (key `dyce.hub.token`), and the last tool and menu item used under `dyce.hub.where`.

A navy rail down the left shows each tool the person may use, with the open tool's menu beneath its name, and the signed-in address and Sign out at the foot. Clicking another tool's name opens it with its menu showing; clicking the open tool's name folds its menu away or brings it back, leaving the page as it is (`tools/rail-preview-check.js`, run by `tests/test_build.py`, checks this in a headless browser); a line above the content says where you are. A soft glow of the Stage magenta tint sits behind the current menu item and follows the pointer or keyboard focus over the rail, and a row under the pointer in the content fills with the magenta tint with a magenta rule on its left edge (Phil Brook's choice, 13/11/2026; the gradient agreed with Chris Beardsmore). At phone width the rail sits above the content. What a person sees follows their ticks, set in DNA Admin; the database checks the tick again on every call, so hiding a tab or menu item is tidiness, not the gate.

| Tool | Tick | What it allows |
|---|---|---|
| Broker Emails | Request | The *Price emails* menu: New email (choose the email, the document, the brokers and who approves it, send now or later), Recent sends, Bounced addresses |
| Broker Emails | Approve | Being offered as an approver, and approving from the approval email's link (index.html). Approve alone shows no menu items |
| Broker Emails | Renewals | The *Renewals* menu: Next 10 days, Recently sent, Stopped brokers (with Stop a broker); stop or restart a renewal email or a broker, always with a reason |
| Dashboard Pool | Review | Boards and Summary: voting Keep, Maybe, Drop or Pass on each candidate board, with audiences and a note, and seeing everyone's votes and the decisions |
| Pricing | View | The Pricing tab and its three screens, read only: Supplier files (every file with its state, and the files that did not load), Band sets and splits, Live price book; the Price this file workspace with its preview, without saving or applying |
| Pricing | Load supplier files | Load a supplier file by hand (the Load a file card on Supplier files); files normally arrive from SharePoint through the loader |
| Pricing | Set margins and splits | Edit the band ladder; make, edit, save and retire band sets; make, edit and retire bundles; save and publish splits; save the margins edited while pricing a file |
| Pricing | Publish | Apply a choice of band sets to a file (Price this file), abandon a set whose build failed, make the Broker and UD Upload files again |
| Commission Engine | View | The *Monthly run* menu: Lines, Exceptions, Decisions and Runs, read-only (no Decide, Enter uplift, Set broker, Fix or Rebuild) |
| DNA Admin | DNA Admin | People and access (the grid of people and ticks), Who may sign in, Sign-in history, Changes made here |

**Pricing.** The tab calls the `dna-pricing` function (`/functions/v1/dna-pricing`, a POST with `op` and the hub session `token`); the function checks the session and the op's tick every time, so hiding a screen or a button is tidiness. It has three screens. *Supplier files* lists every file newest first with the state the database gives it: Loading, Awaiting bandings, Applying, Live, Replaced, Load failed, or Loaded before the pricing tool. Files arrive from the Partner Sales SharePoint folders through the pricing loader in dyce-data-pipelines; a file the loader could not read is listed under *Files that did not load* with the reason. The Load a file card (Load tick) still loads a file by hand: it reads the workbook in the browser (SheetJS and the adapters in `pricing/adapters.js`), stores the original through a signed link, sends the rows in parts under 900,000 bytes of JSON and shows the load report. The newest finished file of each supplier and fuel, whatever its state, has *Price this file*, which opens the workspace: choose band sets (by bundle or one by one, the same for acquisition and renewal or each chosen separately, one per product in each sale type), see the supplier's published splits read only, edit the chosen sets' margins in the grid (held in the page until Apply), and read the preview (`preview_selection`): the proposed prices beside the live book's at the usages given, with the items needing attention, refreshed a moment after each change. If only acquisition or only renewal has band sets, the page says that the other side will have no prices once applied. *Apply* saves each edited band set first (as a new version, or as a new band set, with one reason), can save the choice as a bundle, previews again with the saved margins and refuses, keeping the edits, if the list of items needing attention is not the one the person read; it then sends the count and fingerprint of the list that was read, and the box "I have read the N items needing attention" must be ticked when N is above zero. Each Apply replaces the whole live set for that supplier and fuel. After an Apply the page checks the book every 10 seconds for up to 5 minutes, then makes the Broker and UD Upload files for each new electricity run (`pricing/exports.js`), stores them and records them. *Band sets and splits* is one screen for one fuel at a time: each supplier's splits (publishing a split reprices nothing; electricity only), a grid with a column per band set grouped by bundle and a row per band of the fuel's band ladder (layer switch margin p/kWh or standing charge share %, the annual margin at the band midpoint under each margin, select / shift by / set to / copy column / paste from Excel, changed cells highlighted), a chart of up to four band sets with draggable points, and a cell detail with version history and Restore as a new change. Save changes asks for one reason and saves every changed band set together (`band_sets_save`); New band set, New bundle, Edit bundle members, Edit ladder, Retire band set and Retire bundle need the Set tick. Band sets belong to no supplier: one set is used on any supplier's file. Every save and every preview item carries the ladder the screen was opened with, and the database refuses it if the ladder has changed since. A band set saved against an older ladder is marked *Older ladder* and its margins are carried to the current ladder where a band keeps its lower bound; if every band was carried it counts as changed and the next save saves it on the current ladder, otherwise its blank bands must be filled first, and until then it cannot be applied. *Live price book* shows the live runs, any build problem with Abandon this set, and Make the files again; a recorded Broker or UD Upload file has a Download button, which asks `output_link` for a 60-second signed link and opens it. The page never activates a file and keeps nothing in browser storage. `build.py` puts `vendor/xlsx.full.min.js`, `pricing/adapters.js`, `pricing/exports.js` and `pricing/grid.js` (the grid's pure functions) into the page at `{{XLSX_LIB}}`, `{{PRICING_ADAPTERS}}`, `{{PRICING_EXPORTS}}` and `{{PRICING_GRID}}`, with the modules' `export` keywords stripped and every non-ASCII character written as an escape. In the preview, `?as=pricing` (all four ticks) and `?as=pricingview` (View only); its answers are invented. `python build.py --demo` writes `demo/pricing-demo.html` (git-ignored): the same page with the stub in demo mode, signed in as an invented person, with invented files, margins and prices, kept for the browser tab, and no request to any host.

**Mailing groups.** Step 3 of New email opens with a menu, *Who is it for?*: *Broker primary email (HubSpot company)* (the default, the brokers list as before) or *Broker Contact Segment*. Choosing the segment calls `segment_refresh`, shows the stored copy from `segment` at once, then asks `segment` every 2 seconds for up to 60 until the run has finished (told apart from the earlier run by its `started_at`, never by the browser clock), and ticks every contact. A line above the list gives the time of the copy in London time, or the failed fetch and the copy still shown; *Fetch again* repeats it. The list has the columns Email, Primary Associated Company ID and Name, and search matches any of them. Ticks are kept apart for each group and cleared when the group changes. Requests and previews carry `recipient_group` and either `broker_keys` or `contact_ids`, never both. Recent sends names the group of each send (a send with none was to broker primary emails) and Use again restores it. The approval page says `N addresses in the Broker Contact Segment` for a segment send. In the preview, `?segmentfail=1` makes the stub's fetch fail.

The Renewals items show what the renewals journey will send at its 09:30 weekday run in the next 10 days, grouped by the day each email goes, with the reason for any that will not go; the renewal emails already sent, 50 at a time, each viewable as stored in a sandboxed frame; and the stopped brokers. They never send anything, and while the journey's redirect is set they say where every email goes. They call the `renewals_*` actions of `comms.web_call`; the Price emails items call its broker email actions.

The DNA Viewer tab is the laptop contract library moved into the hub, behind three ticks: View (search, account pages, reporting, opening documents and invoices), Review queue (the queue, a folder's page and its actions) and Originals (opening a file's original, with its bank details). Its pages come from the dna-viewer function and are shown only after the page's allowlist sanitiser.

The Commission Engine tab is the laptop's commission app moved into the hub one piece at a time, behind the `commission.*` ticks; piece 1 is View, read-only. Its pages (Lines, Exceptions, Decisions, Runs and the run, line and decision they link to) come from the commission-engine function as `{title, html}`, and are shown only after the same allowlist sanitiser as the DNA Viewer's. Links and filter forms become page calls to the function with their path and every value of every parameter (`{name: [values]}`, so ticking two choices of a filter sends both); only the function's seven paths are followed. The Broker filter's search hides names in the page as you type, never a ticked one, and asks the function nothing. A link that moves the page under another menu item (a line's run, a decision's line) moves the menu mark, the line above the content and `dyce.hub.where` with it. Nothing from these pages is stored: localStorage keeps only the hub's `dyce.hub.where`, and sign-out empties the tab.

The Dashboard Pool tab is the voting round on the candidate dashboards, behind one tick, Review; the decider (Phil Brook, whose address is written only into the database function) sees the tab without it. *Boards* lists the boards by area in the side menu with each person's own mark (Keep, Maybe, Drop, Pass or To review) and any decision, and shows the chosen board's screen, how each question is answered, the vote (with audiences on Keep and Maybe, and a note) and everyone's votes; *Summary* gives every board's counts and decision. It calls the `pool_*` actions of `comms.web_call`. The boards, figures and votes are held in the page's memory only and dropped on sign-out; localStorage keeps only the open board's id (`hub.pool.board`). `me` says who decides (`is_decider`, true for the decider alone), so the tab shows for the tick or for `me.is_decider`, and nobody without the tick asks `pool_state`.

**Dashboard Pool decisions.** The decider's parts follow `me.is_decider` in `pool_state`, which also carries, for the decider only, `reviewer_count` and `current` on each vote. Each board shows *N of M reviewers have voted* (current reviewers with a vote, Pass included, of all current reviewers; a count only, never who has not voted), the audiences picked with how many picked each, and each vote by someone no longer a reviewer marked *(former reviewer)*. *Your decision* has audience ticks, starting from a kept decision's audiences or else the most-picked audiences, then *Keep this board* (`pool_decide` with the ticks), *Drop this board* (`pool_decide` with none) and *Clear decision* (`pool_clear`); a tick alone saves nothing. *Votes changed since decided* shows beside the decision, in the board list and in the Summary when a vote is newer than the decision (a vote sent again unchanged keeps its time); saving the decision again, changed or not, is always sent and clears it, as the server gives the decision a new `decided_at`. The side menu adds the filters *Awaiting decision* (no decision yet) and *Votes changed since decided*; the Summary adds *N of M voted*, the flag, and a *Reviewer* filter that shows one person's votes. In the preview, `?as=admin` is the decider with the tick, `?as=reviewer` a reviewer, and `__stub.poolVote(email, board, verdict, audiences, note)` in the console records a vote by someone else (for example Sam Example after a decision), shown when the tool is next opened.

`hub.html` is built from `hub.src.html` by `python build.py`, which embeds the logos from `assets/` and inlines the files in `parts/` named in `build.py`'s INCLUDES (`{{POOL_LIB_JS}}`, `{{POOL_SCREEN_JS}}`, `{{POOL_SCREEN_CSS}}`: the Dashboard Pool's helpers and board screen; `{{COMMISSION_JS}}`, `{{COMMISSION_CSS}}`: the Commission Engine tab, its module inlined inside the hub's script); the Pricing modules are inlined from `vendor/` and `pricing/` as described under Pricing, and `node --test pricing/*.test.js` runs their tests. `python build.py --preview` also writes `preview/hub.html` (git-ignored) with `tools/preview-stub.js`, which answers in place of comms-web with made-up people and brokers; choose who signs in with `?as=admin` (every tick, Commission Engine View included), `requester`, `requestonly`, `renewalsonly`, `approveonly`, `adminonly`, `viewer` (DNA Viewer View only), `pricing` (all four Pricing ticks), `pricingview` (Pricing View only), `reviewer` (Dashboard Pool Review only), `decider` (Admin Example, the preview's decider, without the Review tick) or `none`; `?poolempty=1` makes the Dashboard Pool answer as not yet loaded. The stub's Commission Engine pages are drawn by the function's own views over invented values: `node tools/ce-preview-pages.mjs <dyce-spine>/supabase/functions/commission-engine` writes them into the stub (no database is used); run it again when the function's views or fixtures change. `python -m unittest discover -s tests` runs the build tests and `node --test tests/*.test.js` the Dashboard Pool helpers' tests; the sanitiser test and the Dashboard Pool and Commission Engine preview checks (`tools/pool-preview-check.js`, `tools/ce-preview-check.js`) run in a headless Chrome or Edge (or the browser `DV_BROWSER` names) and are skipped when none is found.

Source of the logic: Dyce-Energy-Ltd/dyce-spine, supabase/functions/comms-web and the `comms`, `hub` and `renewals` schemas. Data class: Red (it shows names and addresses after sign-in). Owner: Phil Brook.

## send.html: forwards to the hub

The broker emails page is now part of the DNA Hub. `send.html` only forwards the browser to `hub.html` (a meta refresh and a link); it has no script. The hub removes the old page's localStorage keys (`dyce-send-token`, `dyce.tab`) when it opens.

## The shared origin

All GitHub Pages sites of the Dyce-Energy-Ltd organisation share the origin `https://dyce-energy-ltd.github.io`, so they share the hub's localStorage and the comms-web CORS allowance. **No other repository in the organisation may enable GitHub Pages** unless the hub first moves to its own domain.
